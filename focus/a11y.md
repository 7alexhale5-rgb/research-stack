# Focus lens: a11y (accessibility)

Use this lens when anything is rendered for people. It ties every claim to a WCAG 2.2 success
criterion and, in audit mode, to a measured result on the real page.

## Triggers

Suggested when the topic mentions a11y, accessibility, accessible, WCAG, screen readers, ARIA,
colour contrast or keyboard navigation. Bundles: `#launch`, `#ship-audit`.

## Sub-question lens

1. **Criteria in play:** which WCAG 2.2 A/AA success criteria apply to this component or flow,
   and which are new in 2.2 (focus appearance, target size, dragging, redundant entry)?
2. **Pattern:** what is the correct ARIA Authoring Practices pattern (keyboard model, roles,
   states), and which common implementations get it wrong?
3. **Legal and market bar:** which regime applies (ADA, EN 301 549 under the European
   Accessibility Act, Section 508), and by what date?

## Tool stack

| Tool         | Tier       | Use it for                                                     | Skip when                    |
| ------------ | ---------- | -------------------------------------------------------------- | ---------------------------- |
| `w3c-wai`    | free       | Normative success criteria, Understanding docs, ARIA APG       | never                        |
| `axe`        | free (CLI) | Automated rule checks with selectors                           | no target to run against     |
| `lighthouse` | free (CLI) | Accessibility score and failing audits                         | no target                    |
| `playwright` | free (MCP) | Keyboard-only walk, focus order screenshots, axe in the page   | no target                    |

All four are free, so this lens never needs paid tools. Deque's official axe MCP server needs a
paid subscription; run axe-core through Playwright instead. Pair it with the `legal` lens when the
compliance deadline is the real question.

## Authorities

w3.org/WAI (WCAG 2.2, Understanding, APG) is normative. WebAIM and Deque are strong secondary
sources. Overlay vendors' marketing is not evidence of conformance.

## Freshness

- Cache TTL: 180 days for criteria, 30 days for legal deadlines.
- Dated trap: automated tools catch only part of the issues. Never report "accessible" from an
  axe pass alone; say what was tested by hand.

## Audit mode

With `--target <url>`: run `axe` (via `@axe-core/playwright` or the CLI) and `lighthouse`
accessibility. Do a keyboard-only pass with `playwright` (tab order, visible focus, escape closes
dialogs). Check text contrast on the main template. Tag `[AUDIT:axe]` and `[AUDIT:lh]`.

## Report addendum

Add an **Accessibility checklist** section:

```text
### Accessibility checklist
| WCAG 2.2 SC              | Level | Status (tested how)          | Evidence / selector          | Source       |
| ------------------------ | ----- | ---------------------------- | ---------------------------- | ------------ |
| 2.4.11 Focus Not Obscured | AA   | fail (keyboard walk)         | sticky header covers focus   | [AUDIT:pw]   |
| 1.4.3 Contrast (Minimum) | AA    | fail (axe)                   | .btn-secondary 3.1:1         | [AXE]        |
```

## Pathway mapping

- pathway-operating-layer: `design`, `quality`, plus the `ui-proof` overlay.
- development-protocol rows: `research`, `design`, `verify` (the checklist becomes test cases).
